## 1. 已完成

- 使用 `uv` 建立项目隔离的 CPython 3.11.15 环境，不改变系统 Python 3.13；
- 生成并锁定 `uv.lock`，当前关键依赖为 MediaPipe 0.10.35、OpenCV contrib 4.11.0.86、NumPy 1.26.4、psutil 7.2.2；
- 配置校验：640×480、15 FPS 摄像头，Face 8 FPS、Pose 4 FPS、Object 1.5 FPS；
- 摄像头在后台线程运行，帧缓冲只有一个槽位，新帧覆盖旧帧，不产生延迟队列；
- 检测 MSMF 在当前执行环境中启动阻塞后，将目标电脑默认后端改为 DirectShow；
- 下载并校验 Google 官方 Face Landmarker、Pose Landmarker Lite、EfficientDet-Lite0 int8 模型；
- Face、Pose、Object 使用同一最新帧但独立限频；Object 只输出 `cell phone` 类别；
- 运行时无视频预览，不写入图像或视频；
- 建立 Windows 0–100% 口径的进程 CPU、内存和预算汇总；
- 11 项配置、帧缓冲、摄像头超时、模型哈希和资源预算单元测试通过。

### 3.2 摄像头 + 三个预训练模型

30秒稳态验证，Face/Pose/Object 目标频率分别为8/4/1.5 FPS：

| 模块 | 运行次数 | 实际约频率 | 平均延迟 | P95延迟 | 正检帧 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Face Landmarker | 193 | 6.43 FPS | 14.79 ms | 29.91 ms | 141 |
| Pose Landmarker Lite | 97 | 3.23 FPS | 19.87 ms | 29.94 ms | 97 |
| EfficientDet-Lite0 int8 | 43 | 1.43 FPS | 65.39 ms | 75.44 ms | 0 |

整段测试摄像头抓取419帧、读帧失败0次；进程 CPU 平均4.27%、P95为5.66%，峰值内存245.5 MB。对应验收预算是平均15%、P95 25%、内存500 MB，因此当前组合有明显余量。

Face 正检141/193不直接等于模型准确率：这次没有逐帧真值标注，使用者也未被要求始终正对画面。Pose 在97次运行中均检测到单人。测试期间未安排手机进入画面，因此 Object 的0个正检只表示缺少正样本，不能用于判断手机检测能力。

短于15分钟的测试不会外推每小时内存增长；60分钟稳定性测试仍是发布前必需项。

## 4. 已发现并解决的问题

1. 同时安装 `opencv-python` 和 MediaPipe 间接依赖的 `opencv-contrib-python` 会共享 `cv2` 文件，卸载其中一个可能破坏另一个。项目现在只保留 contrib 包并写入锁文件。
2. 当前 OpenCV 构建没有 `CAP_ANY` Python 常量，自动后端使用OpenCV定义的数值0。
3. MSMF 在目标执行环境中打开摄像头会阻塞；DirectShow 可以稳定抓帧，因此当前目标电脑默认使用 DirectShow。
4. 摄像头启动失败或超时现在会立即返回明确状态，不再继续空等测试时长。
5. 短测试的少量内存变化不能按比例外推到一小时，资源报告在不足15分钟时返回 `null`。

## 5. 第一阶段剩余门槛

- 在明确操作脚本下采集“不拿手机、桌面放手机、短暂拿起、持续手持、相似物体”场景，只记录人工标签和模型框/分数，不保存连续视频；
- 连续运行60分钟，验证 CPU、P95、峰值内存、内存增长和摄像头恢复；
- 把原始结果转换为统一 `Observation`：Face/头部、肩腕姿态、手机框、图像质量和可观测状态；
- 验证在系统繁忙/电池模式下的降频档位；
- 摄像头采集最终隔离到可重启进程，避免驱动调用阻塞整个桌面应用。

这些通过后进入规则引擎阶段：在席、明显离开屏幕方向、相对基线姿势偏离、手机手持关系、持续时间、迟滞、提醒冷却和扣分账本。
