## 当前生效范围：用户确认的极简首版

用户在初版计划后明确要求功能和界面极简、按需扩展，并授权开始实现。以下约定替代本文后续原完整方案中冲突的要求；后续各节保留为未来扩展参考，不再全部作为首版验收条件。

- 只做单次任务：名称、带时区开始时间、时长；暂不做每周重复、复杂休息策略、规则配置界面或复杂冲突仲裁。
- 会话只提供开始、暂停/继续、结束和自动到时结束；暂停不顺延计划结束时间。
- 使用SQLite保存会话、聚合时长和事件/实际扣分；事件通过action的event_id关联，不额外建立无消费者的数据层。
- 结束和历史查看仅显示摘要、分项覆盖和主要事件；不导出JSON/HTML，不做趋势图或独立报告文件。

- 暂用一个控制台窗口，不建设IPC服务；当前会话的控制命令只在运行窗口输入。其他终端可添加任务、查看历史和修改截图开关。
- 正式极简桌面界面归E；用户确认PySide6路线并要求继续后，基础窗口已先行实现，一个主界面和历史列表复用SessionService，其余E功能未提前扩展。
- 模型/参数继续冻结；D数据库与研究目录隔离。最小真实集成已完成，产品长时负载检查仍需完成，可靠性测试不因功能简化而取消。

## 1. 目标与依据

交付一个可通过 CLI 实际使用的本地闭环：创建任务 → 到点建立会话 → 接收观测 → 提醒动作与解释性扣分 → 保存事件和少量证据 → 结束后查看报告 → 按策略清理数据。服务层供 E 阶段桌面界面直接调用。

当前依据按优先级为：9 月 10 日的 phase-c-window-handoff.md、phase-c-complexity-review-20260910.md、phase-c-closeout-audit-20260909.md、实际配置与代码。9 月 8 日审查中的 S216/S240、Person 缺失和旧注意力扣分描述属于历史状态，不能作为 D 的当前前提。

C 已有两轮 5 分钟自然使用和冻结后的离席/手机事件链证据；仍需 144 秒最小盲测、有效 60 分钟无录像长测及最终确认。D 主体开发不以这三项完成为前提；真实整体效果与完整负载验收需使用最终确认的 C 版本。

## 2. 范围与产品口径

### 本阶段交付

- SQLite 数据模型、版本迁移、事务与仓储；
- 单次和每周重复 Agenda、一次到期只建立一次会话；
- 会话开始、暂停、继续、计划休息、结束、异常中断；
- 规则配置快照、任务豁免、事件与扣分持久化；
- 分项覆盖率、规则遵守度、软提示与事件报告；
- 本地事件关键帧、配额、保留期限、按会话删除和删除全部产品数据；
- CLI 操作及可供 E 调用的应用服务接口；
- 单机单实例运行和进程重启后的数据一致性。

### 交给 E/F

正式 PySide6 界面、托盘、系统通知/浮层/声音通道、Windows 锁屏/睡眠事件接入、摄像头子进程隔离与完整重连、电池自适应、安装包、自启动、升级回滚、备份界面和静态加密。D 实现这些功能需要的状态/API，但不把它们记为已完成。

D 的 CLI 提供可见的任务/规则提示；实际桌面通知体验由 E 完成。后台程序未运行时，D 不承诺唤醒电脑或自动执行任务。

### 沿用冻结语义

| 信号 | 触发与默认后果 |
| --- | --- |
| away | 连续 20 秒，初扣 3 分，单项会话上限 15 分 |
| phone_held（内部兼容名） | 清晰可见手机候选连续 10 秒，初扣 5 分，每额外 60 秒扣 2 分，上限 25 分 |
| attention_away | 8 秒软提示，零扣分，300 秒提示冷却 |
| posture_deviation | 20 秒健康软提示，零扣分，300 秒提示冷却 |
| ergonomic_risk | 30 秒健康软提示，零扣分，独立呈现 |
| unknown / exempt | 不累计违规时间、不扣分；分别解释观测不足与允许行为 |

面向用户显示“可见手机”，不显示“已确认正在玩手机”。手机未检出不证明没有使用手机。D 不自动把旧配置中的注意力/姿态非零扣分恢复为默认；导入旧配置时显示差异，软信号非零扣分配置拒绝启用并说明原因。

## 3. 与 C 并行的接口和隔离

复用现有 Observation、SignalValue、RuleConfig、SustainedRule 和 RuleAction；不另建视觉状态体系。保留 phone_held 内部名称，显示名称在产品层映射。

新增边界只服务实际消费者：

| 接口/对象 | 内容与约束 |
| --- | --- |
| ObservationSource | 启停、读取 Observation、报告源健康与有效能力；提供合成序列和冻结视觉管线两种实现 |
| SessionContext | 会话 ID、任务实例、运行状态、各规则豁免、规则策略版本；在规则处理前应用 |
| RuntimeIdentity | 代码快照/dirty 标记、模型与配置哈希、校准 ID、启用能力；按会话保存 |
| SessionService | start/pause/resume/break/end；是 CLI 和未来 UI 的唯一业务入口 |
| NotificationSink | 接收稳定 action ID、级别、原因；D 使用控制台，E 替换呈现通道 |
| EvidenceProvider | 仅在事件请求时提供当前帧及时间；默认关闭连续帧存储 |

摄像头和模型只属于视觉适配器。Agenda、数据库、报告、扣分服务不能导入 MediaPipe/ONNX/Ultralytics。

D 使用独立 data/product/ 数据根目录，绝不把 C 的 data/formal、data/natural、data/training 或历史证据纳入自动清理。保留 C 模型和校准文件只读。

并行开发优先新增 storage/、sessions.py、agenda.py、reporting.py、evidence.py、runtime.py 等业务模块；对 rules.py、scoring.py、cli.py 的共同修改集中在集成点进行。实施前保存可复现的 C 工作树快照及哈希清单；若使用独立 checkout，应包含当前未提交候选，不能仅从旧 HEAD 开始。C 验收进程与 D 视觉运行不同时占用摄像头，C 长测期间不运行 D 压力测试。

## 5. SQLite 最小数据模型

优先标准库 sqlite3、显式 SQL 与顺序迁移脚本，避免本阶段额外 ORM/通用插件框架。采用短事务、单写入路径和外键；WAL 与忙等待参数在目标 Windows 环境测试。模型推理、截图编码和通知不放在数据库事务内。

| 表 | 核心字段/职责 |
| --- | --- |
| schema_migrations | 版本、应用时间 |
| tasks | 标题、时区、计划时长、单次时间/每周重复、开始提醒提前量、休息策略、启用状态、规则策略引用 |
| task_occurrences | task_id、scheduled_at_utc、状态、关联 session_id；任务+计划时刻唯一 |
| rule_policies | 版本化规则与豁免配置；已开始会话使用不可变快照 |
| sessions | 任务实例、UTC 开始/结束、终止原因、规则/模型/代码/校准快照 |
| session_intervals | 监控/暂停/休息/故障区间，以及各信号连续状态的聚合区间 |
| events | 会话、规则、事件起止、状态、触发阈值与解释；保留软/硬类型 |
| actions | 稳定 action_id、事件 ID、kind、事件内序号、发生时刻；唯一约束避免重复处理 |
| penalty_ledger | action_id 唯一、实际扣分、被抑制原因、策略版本 |
| evidence | 事件、相对路径、时间、哈希、到期、大小、写入/删除状态 |
| settings | 保留期、图像开关、配额、默认时区及 schema 化配置 |

每个输入样本不永久逐帧落库：连续状态聚合成区间，事件保留必要统计。报告读取持久化事实，不依赖仍在内存的 PenaltyLedger。历史 C JSONL 不批量自动导入产品库，测试回放使用明确适配入口。

## 6. 关键行为约定

### 会话与恢复

状态为 waiting_for_source、monitoring、paused、break、ended、interrupted。任务到点先建立会话，再预检必要源。硬信号所需模型/摄像头不可用则等待，不计作用户离席；软信号校准缺失可禁用该能力并明确展示，不强迫每次任务重做 17 点校准。

暂停、休息、豁免生效时终止对应待触发计时；已有事件按原因关闭。恢复后从新鲜观测重新计时，不能把暂停前后的手机片段拼成持续违规。采集故障区间保留为 unknown，已激活事件遵循现有 unknown grace，不补记断流时间。

进程重启后把未完成会话标记 interrupted，保存已经提交的扣分；不跨进程连接 monotonic 时间，不把停机时间算违规，不自动恢复摄像头。用户可选择继续任务并创建关联的新会话。UTC 用于存储日期，monotonic 用于本次进程计时。

### Agenda

按既有选型使用 APScheduler 3.11.x 适配器，实施时核对官方接口并锁定依赖；业务数据库作为任务与执行状态的唯一来源，启动时重建未来调度，避免两套持久化日程相互漂移。

建议默认：单次和每周指定星期/本地时间；运行中 60 秒内的调度迟到允许启动一次，超过窗口标为 missed 并提示用户手动开始；进程重启不自动补开历史摄像头会话。DST 不存在的本地时刻跳过并标注，重复时刻只执行第一次。修改任务只影响未来实例，已开始会话快照不变。

同一时刻只运行一个摄像头会话。发生重叠任务时记 conflict 并提示选择，不暗中中止当前任务、不并行抢摄像头。到计划结束时自动结束；用户可提前结束或在结束前延长。休息由 SessionService 定时进入和退出，CLI 可以取消/延长。

### 扣分与覆盖率

本阶段继续使用 100 分减实际硬规则账本，不恢复预研加权 attention/posture 公式。健康与注意力零效率扣分。增加明确的策略仲裁入口：默认 away 优先于同时激活的 phone_held，重叠期间保留手机事实但抑制重复提示/处罚；该默认是 D 的新产品策略，不追溯修改 C 的原始测试。新增规则需配置冲突组与优先级，未来也不能因相同动作多路信号重复扣分。

幂等持久化以 action_id/序号为准；事件、action 和实际账本在同一事务提交。先提交再通知；通知投递单独标记，重试不再扣分。事务失败时停止该会话后续计分并进入故障状态，不能继续产生无法落库的处罚。

每信号分别统计 eligible、compliant、violation、unknown、exempt 时长：暂停/计划休息/对应豁免从 eligible 分母排除；监控期断流仍在 eligible 内且记 unknown。coverage=(compliant+violation)/eligible。总分有效性采用启用硬规则覆盖率的最小值，软信号覆盖率不否决硬规则总分。硬规则 coverage<80% 或没有可计分时段时，报告显示“证据不足”，账本可查但不展示有效总分；无启用硬规则则显示“仅观察”。

### 证据与删除

建议产品数据默认保留 30 天、图像可关闭、每事件最多 3 张、全局图像配额 500 MB；均可配置。指标本地保存，不存连续视频或完整 landmarks。照片满额/写入失败仅记 evidence_unavailable，不阻断事件与账本。

证据先写临时文件后原子改名，索引跟踪 pending/ready/failed；启动时处理孤儿临时文件和缺失索引。清理按 pending_delete→删除文件→删除关联记录执行，可重试并诚实报告未删项，不声称跨数据库/文件系统原子事务。路径必须解析后仍位于 data/product/evidence；符号链接/目录联接越界拒绝处理。

“删除全部产品数据”只作用于 data/product，不触碰 C 研究数据、模型、源码或校准原件。产品清理不代替用户对历史调试录像的删除决定。

## 7. CLI 与最终演示

建议命令族（尚未实现）：

- observer task add/list/show/update/disable/delete
- observer run：保持调度与产品运行服务；后台驻留/开机启动留给 E/F
- observer session start/status/pause/resume/break/exempt/end
- observer report show/export：按会话查看或导出 JSON/本地 HTML
- observer data status/purge/delete-session/delete-all

独立 CLI 命令需通过本地控制入口联系唯一运行服务；选择简单的本机 IPC 实现，必须验证权限和单实例归属，不开放外网 HTTP 服务。

验收演示：创建一分钟后的短任务 → 到点启动合成观测 → 手机持续触发一次扣分 → 暂停期间不扣分 → 恢复并结束 → 重启后报告与账本仍一致 → 删除会话后其图像和记录一致消失。真实适配完成后用同一服务替换合成源做一次短集成，禁止另造产品专用判定算法。

## 8. 测试与阶段完成条件

确定性测试使用可控时钟和临时 SQLite，不要求用户为状态机长时间保持动作。必须覆盖：

1. 触发前/触发时/恢复/unknown/豁免/暂停边界；软规则持续异常仍零扣分；
2. 重复提交、通知重试、重启、事务回滚与唯一执行实例；
3. 任务编辑/取消、时区/DST、迟到、重叠及计划休息；
4. 有效覆盖率边界、零样本、分项时长与账本重建；
5. 图片关闭、写入失败、配额满、删除失败重试与路径越界；
6. 推理线程/采样故障不能制造离席扣分，磁盘错误不能静默漏记；
7. 冻结视觉适配确实加载指定 YOLO 与 Person 探针，未改 C 参数。

持续运行目标：D 服务 API 普通操作目标小于 100 ms（图像编码不在响应关键路径）；队列有界、无逐帧 DB 写入。C 的长测证明感知基线；D 集成后另做实际调度/写库/截图负载测量，仍对照总 CPU 平均15%/P95 25%、内存500 MB/小时增长50 MB预算，不拿 C 无产品负载结果替代。完整 UI 负载长测留给 E。

D 的业务模块可在 C 最终确认前完成工程验收；D 阶段整体通过需满足：本计划闭环可演示、故障/时序测试通过、C 最终版本或明确有条件接受范围已对齐、真实集成及资源检查完成、产品文档/结果报告齐全，并由所有者确认。不能把“D 主体开发完成”写成“感知和完整桌面产品已发布”。
