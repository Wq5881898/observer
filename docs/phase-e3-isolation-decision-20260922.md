# E3 摄像头与推理隔离决策

日期：2026-09-22  
结论：当前阶段保留单个产品工作线程拥有摄像头与模型；不实施生产子进程。保留已验证的子进程方案作为故障触发后的回退路线。

## 测量方法

`scripts/measure_e3_isolation.py` 在目标电脑使用冻结模型、不打开摄像头，分别测量单进程、模型仅在子进程、父子重复加载、真实 Qt 桌面预热和无模型桌面壳。脚本输出 JSON，子进程就绪与关闭读取均有超时，异常时强制回收测量子进程。

另运行 `python -m observer product check --seconds 15`，打开真实摄像头、冻结模型、产品会话与资源采样；不保存视频或正常时段图像。

## 结果

| 场景 | 就绪内存 | 加载/就绪 | 关闭/退出 |
| --- | ---: | ---: | ---: |
| 单进程模型栈 | 267.7 MB | 3.578 秒 | 模型关闭 0.032 秒 |
| 模型仅在子进程（测量父进程 + 子进程） | 291.7 MB | 1.547 秒 | 子进程完整退出 0.203 秒 |
| 父子各一份模型 | 541.1 MB | 父 1.969 秒、子 1.859 秒 | 超过 500 MB 预算 |
| 无模型 Qt 桌面壳 | 62.1 MB、9 线程、264 句柄 | 0.172 秒 | 0.031 秒 |
| 当前 Qt 桌面预热模型 | 322.4 MB、45 线程、564 句柄 | 6.329 秒 | 0.078 秒 |
| 真实摄像头产品短检 | 峰值 385 MB | 15 秒观测 | 正常结束，退出码 0 |

真实短检 CPU 平均 9.8%、P95 14.7%、4 个资源样本；覆盖 36%，因此诚实显示证据不足。短检只验证启动、观测、资源与释放接线，不替代 60 分钟门。

不同运行的操作系统缓存会影响加载时间，内存结论比单次耗时更稳定。关闭模型后 Python/原生分配器不会把所有内存立即归还操作系统，这不等于资源对象仍被使用。

## 决策理由

当前桌面和真实短检均低于 500 MB，正常退出远低于 1 秒；D 的 60 分钟真实产品门也已通过。把唯一模型移入子进程的估算总内存约为无模型桌面 62 MB 加模型子进程 268 MB，即约 330 MB，技术上可行且不会必然超预算。

但生产拆分还必须为 Observation 序列化、个人基线进度、启动取消、一次重连和按需证据帧建立新 IPC。持续传输原始帧会扩大内存、延迟和隐私面；按需取帧则需重构现有证据调用。当前没有真实证据证明正常路径无法有界释放，立即拆分增加的回归风险高于已观察到的收益。

因此本阶段采用现有单产品工作线程，加上长停顿连续性保护、一次摄像头重连、启动取消和明确中断行为。这个决定不改变 D 的模型、Observation、证据、评分或单一数据库所有者语义。

## 启用子进程的触发条件

满足任一项即重新打开隔离实现：

1. 真实睡眠/唤醒或拔插测试中，摄像头/推理调用超过 10 秒不返回，主窗口无法显示恢复状态；
2. 明确退出超过 5 秒仍未释放摄像头或运行锁，且原因位于原生摄像头/模型调用；
3. 摄像头或模型异常导致整个 Qt 进程崩溃；
4. E5 长测出现不能由现有重连和连续性保护恢复的重复设备故障。

触发后采用“父进程独占 Qt、数据库、会话、计划、计分与 RuntimeLock；一个子进程独占摄像头和唯一模型栈”的边界。父进程不得预热第二份模型；Observation 使用有界消息，证据帧仅按需返回，不开放通用网络服务。
