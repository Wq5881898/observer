# YOLO11n 历史录像诊断报告

日期：2026-09-05
模型：`models/yolo/yolo11n.onnx`
模型 SHA-256：`DFED31EBBCD25F7786830CF420D0C5114984ECD29459256607D7C59508A279FA`
运行时：ONNX Runtime 1.29.0，CPU

## 1. 目的

使用已有 P0/P1 手机边缘录像，检查 YOLO11n 在不同画面位置的候选框是否存在，
并区分“候选存在但置信度低”和“模型没有产生有效候选”。本报告不改变正式
EfficientDet 路径，也不改变 Observer 正式参数。

## 2. 基线阈值 0.25

`data/model-eval/yolo11n-p0` 和 `data/model-eval/yolo11n-p1` 保存逐帧报告。
正例场景中的手机检出帧比例如下：

| 场景 | P0 | P1 | 观察 |
| --- | ---: | ---: | --- |
| 下方中心 | 77.8% | 100.0% | 基本可用，但 P0 仍有漏帧 |
| 左下 | 0.6% | 10.3% | 严重漏检 |
| 右下 | 0.0% | 0.6% | 基本漏检 |
| 上方边缘 | 41.3% | 1.3% | 批次间不稳定 |

恢复段大多数没有检出，但 P0 上边缘恢复段有 9.7% 的手机检出帧，说明误报
风险已经存在。

## 3. 阈值对照

### 0.15

中心正例检出率提高，P0 从 77.8% 提高到 94.1%；但左下/右下仍不能稳定
检出，上边缘恢复段约 50% 的帧出现手机候选，P1 中心恢复段约 30% 出现候选。

结论：降低阈值只能捞出低置信度候选，不能修复边缘位置的稳定性。

### 0.10

部分正例检出率继续提高，但恢复段误检明显增加；部分 P1 录像的平均延迟
达到数百毫秒，P95 延迟达到 1 秒以上，个别观测超过 3 秒。该阈值批次因
资源开销过高而停止，未完成的报告不作为完整矩阵结论。

结论：`0.10` 不适合作为 Observer 运行参数。

## 4. 极低阈值候选诊断（0.01）

诊断报告目录：`data/model-eval/yolo11n-diagnostic-t0.01`。正例检出帧比例：

| 场景 | P0 | P1 | 候选特征 |
| --- | ---: | ---: | --- |
| 左下 | 65.2% | 89.7% | 中位置信度约 0.083 / 0.154，框面积约 0.026 |
| 右下 | 50.6% | 98.1% | 中位置信度约 0.023 / 0.048，框面积仅约 0.001–0.004 |
| 上方边缘 | 94.2% | 49.4% | 中位置信度约 0.070 / 0.133，框面积约 0.044–0.047 |

这说明：

1. 左下和上边缘并非完全不可见，模型经常有低分候选；
2. 右下候选的框面积很小，常常只覆盖手机窄条或局部纹理，不能简单视为
   “漏检只因阈值太高”；
3. 同一场景的 P0/P1 置信度差异很大，存在视角、手机露出比例、运动和画面
   取景变化影响。

代表性证据图位于：

```text
data/model-eval/yolo11n-diagnostic-t0.01/evidence/
```

其中右下样本显示模型可能只框住手机窄条；左下样本可以形成较完整的手机框；
上边缘样本可以框住手机，但同时出现人物/手臂相关候选。

## 5. 与 EfficientDet 历史结果的关系

EfficientDet P0/P1 原始报告位于：

```text
data/formal/phone-edge/P0-control-manual/tuning-20260905T191727Z-e21657a6/
data/formal/phone-edge/P1-control-manual/tuning-20260905T192653Z-1b4fc600/
```

历史 EfficientDet 在 P0 中心场景能形成稳定正例，但左下、右下和上边缘同样
存在漏检。YOLO11n 的优势目前只表现为“在低阈值下能产生更多边缘候选”，尚未
证明它能在相同误报和资源预算下超过 EfficientDet。

## 6. 当前决策

- 不把 YOLO11n 接入正式运行；
- 不把 `0.15` 或 `0.10` 写入正式配置；
- 下一步优先检查输入预处理、框质量和目标像素尺寸；
- 若要训练，必须以左下/右下/上边缘、部分露出和负样本为独立数据集，不能
  直接把当前录像相邻帧混入训练和 holdout；
- 在继续训练前，应先补充逐帧真值框或人工核验标签，否则只能比较“候选存在率”，
  不能计算可靠的检测 precision/recall。
