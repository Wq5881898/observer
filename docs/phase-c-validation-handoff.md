# Observer 阶段 C：设计到真实验证交接与复杂度评分

版本：0.2
日期：2026-08-30
状态：已批准的交接模板；实现期间维护，真实验证后定稿

## 1. 用途

本文件连接“设计/实现”和“真实用户验证”。它防止两种问题：一是实现完成后无法知道怎样验证；二是为了技术完整而长期保留没有实际收益的复杂设计。

阶段 C 的默认方案都视为假设。真实验证后，每项设计只能得到以下结论之一：

- `keep`：有测量证据证明必要或收益明显；
- `simplify`：方向有效，但当前实现成本高于收益；
- `remove`：没有可测收益、产生副作用或已有更简单替代；
- `defer`：当前场景无足够数据，且不影响 MVP 硬门槛，因此移出常驻实现；
- `investigate`：结果矛盾，阶段 C 不能宣称通过。

## 2. 实现交接清单

真实测试开始前，开发侧必须填写：

- 当前 Git 提交 SHA、配置哈希、模型清单哈希；
- 校准档案 schema 与特征版本；
- 可执行命令和预期输出文件；
- tuning/holdout 目录及禁止混用规则；
- 证据策略、保存位置、到期时间和删除命令；
- 已知不可检测区域和所有 `unknown` 条件；
- 当前启用的设计开关或可离线重算的替代方案；
- 自动化测试结果及未覆盖项；
- 目标设备短时性能基线。

任一项缺失，都不能把真实测试结果用于阶段验收。

## 3. 真实验证交接清单

用户侧按校准/验证工具提示完成动作，验证侧必须记录：

- 当天实际布局、光照、电源模式和眼镜状态；
- 每个 trial 是否按说明完成，invalid 原因不得删除；
- 校准、tuning、配置冻结、holdout 和 60 分钟长测的批次 ID；
- 误判关键帧是否获准保存；
- 用户主观感受：提醒候选是否明显烦扰、校准是否过长、动作是否不自然；
- 测试结束后是否完成证据复核和过期删除检查。

## 4. 复杂度评分方法

每项设计分别记录两个 0–3 分：

### 4.1 实测必要性 N

| 分数 | 含义 |
| ---: | --- |
| 0 | 关闭后指标和可解释性没有实质变化 |
| 1 | 只改善少量边界案例，不影响阶段结论 |
| 2 | 明显改善核心指标、误报、unknown 或用户体验 |
| 3 | 不启用就无法达到硬验收线或隐私/安全原则 |

### 4.2 复杂度负担 C

| 分数 | 含义 |
| ---: | --- |
| 0 | 几乎无新增代码、配置、运行开销或维护面 |
| 1 | 小幅增加，接口清楚且测试简单 |
| 2 | 增加明显模块、状态、配置、交互或资源开销 |
| 3 | 引入新模型/依赖、显著性能成本或长期维护风险 |

判定规则：

- `N = 0`：默认 remove/defer；
- `N = 1 且 C ≥ 2`：默认 simplify/remove；
- `N ≥ 2`：可以 keep，但仍需记录是否存在更简单替代；
- 涉及隐私和 unknown 安全语义时，即使准确率收益小，也可以因为安全必要性得到较高 N；
- 不能用代码行数本身证明复杂或简单，重点看概念、状态、依赖、性能和测试负担。

## 6. 阶段末清理门

在生成 `docs/phase-c-result.md` 前执行：

1. 删除结论为 `remove` 的代码、配置、文档和测试；
2. 将 `defer` 项移出默认依赖和运行路径，并记录重新评估触发条件；
3. 对 `simplify` 项完成简化或把阶段结论标为有条件通过；
4. 确认保留项都有自动化测试和用户可理解的理由；
5. 在结果报告中汇总保留的复杂度、删除的复杂度和仍未知的风险。

只有经过此清理门，才能评价阶段 C 是否真正形成了“最小但可靠”的方案。
