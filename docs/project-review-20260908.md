## 5. 代码与文档需要收敛的问题

1. **最新状态缺少单一可信摘要。** README 仍写 9 点和等待真实校准；阶段基准仍写手腕关系、不训练、无连续录像；旧启动 prompt 仍称 D02/D05 未真人复测；联合报告仍写等待 P3b；训练手册仅概括 B06，未完整汇总最新四项失败及 CPU 超线。历史记录应保留并标明被哪次决策取代，当前总览需统一。
2. **冻结版本追溯不足。** 工作树存在大量未提交修改和未跟踪实验文件；`BatchManifest` 只含 Git HEAD、AppConfig 哈希和原 MediaPipe 清单哈希。`validate-live` 的 YOLO 路径/权重哈希及三个 CLI 手机实验参数未进入该 manifest。相同 HEAD/配置哈希不保证相同实验代码或模型。
3. **B06 下一轮准入文字与代码不一致。** 手册写至少 85%（目标 90%）、连续接近 10 秒；`scenario_record_passes` 对 B06 仍要求至少 90% 且连续至少 10 秒。85% 可以作为学习改善指标，不能未经明确变更就当原严格验收通过。
4. **资源配置尚不等于运行能力。** `busy_*_fps` 出现在配置中但未见运行时消费，当前代码主要是采样和报告超标；不能声称已经完成自动电池/负载降档。摄像头采用线程与打开回退，尚不是完整故障隔离与恢复产品。
5. **单类别 YOLO 替换有跨能力风险。** 当前单类别模型只输出 cell_phone，而遮脸在席曾依赖 EfficientDet 同次推理的 person。替换整个 object backend 后会失去该路证据；正式替换必须回归完全遮脸在席/空座，不能只跑手机用例。本项是代码推导的集成风险，尚非本次真人复现。
6. **规则核心尚非最终评分系统。** RuleEngine 独立执行各规则，未实现原始“手机与离屏同段默认不重复扣分”的冲突仲裁；账本为内存数据，尚无完整覆盖率不足时的产品报告降级。需在 D 阶段明确交付。
7. **工程复现仍需整理。** pyproject 新增 YOLO extra，而 uv.lock 未列 onnxruntime；.annotate、.yolo-train、.yolo-export 和根目录权重出现在未跟踪文件中。应整理依赖锁、模型清单及忽略策略，避免误把开发环境纳入交付。

## 6. 简要经验教训

- 训练误差和 mAP 好看不等于真人可用；必须区分训练回放、同设备新会话、新手机和最终独立测试。
- 每次修复都要保住旧能力：边缘手机、完整手机、非手机困难负例和恢复段必须共同回归。
- 调低阈值会同时增加误报，延长候选保留会影响恢复；不能只看正例改善。
- 逐帧比例、连续事件和恢复必须同时看。P3b E01 的 95% 正确帧仍不足以产生 10 秒连续事件，是直接例证。
- 真人动作定义必须独立于模型绿灯；无效输入、unknown、算法失败和已知限制需分别记录。
- 从自然使用条件出发设计取景和校准，避免让用户迎合算法；头朝向、注视方向和健康姿态是不同事实。
- 失败证据和及时回退很有价值，但文档和版本必须同步，否则越积累记录越容易依据旧结论继续工作。
